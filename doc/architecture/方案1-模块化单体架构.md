# 方案 1：模块化单体 + 异步任务队列架构

## 目标

为当前 AI 爆款短视频脚本生成与复刻平台设计第一阶段可落地架构。该方案优先支撑 MVP 到早期商业化：前台 9 步创作工作流、后台运营管控、多租户隔离、合规审核、AI 生成任务和素材管理。

## 当前项目现状

当前仓库已有两个独立 Vite + React UI 设计稿/原型应用，应作为新前端工程的页面参考，不建议直接作为最终生产工程继续堆业务代码：

| 前台 UI 设计参考 | `ui/ui-front-web/` | 用户登录、首页、新建项目、9 步脚本/视频生成工作台的页面原型 |
| 后台 UI 设计参考 | `ui/ui-admin-web/` | 数据概览、解析管理、知识库、审核流、素材、数据看板、系统权限的页面原型 |

## 总体架构

采用“两个生产前端 + 一个模块化后端 + 异步任务 Worker + 共享基础设施”的前后端分离方式。`ui/` 目录只作为页面设计参考，生产代码放到新的 `apps/` 目录。

```text
UI 设计参考层
  ui/ui-front-web/       ui/ui-admin-web/
  前台页面原型            后台页面原型
        |                     |
        v                     v

生产前端层
  apps/front-web/        apps/admin-web/
  前台用户端              后台管理端
        |                     |
        +----------+----------+
                   |
          HTTP API / SSE / WebSocket
                   |
后端应用层
             server/
        模块化单体 API 服务
                   |
        +----------+-----------+
        |                      |
    PostgreSQL              Redis + RQ/Celery
    业务数据/租户            缓存/异步任务
        |                      |
        |                 workers/
        |                 AI/视频/导出任务
        |
    Object Storage
    视频/图片/音频/导出文件
        |
    Vector Search
    结构公式、知识库、相似度检索
        |
外部服务：视频解析 API、LLM、文生视频、TTS、数字人、平台数据 API
```

## 技术选型

### 前端

| 层 | 技术 | 说明 |
| --- | --- | --- |
| 前台生产前端 | React 18 + Vite + TypeScript | 新建 `apps/front-web/`，按 `ui/ui-front-web/` 设计重做真实页面 |
| 后台生产前端 | React 18 + Vite + TypeScript | 新建 `apps/admin-web/`，按 `ui/ui-admin-web/` 设计重做真实页面 |
| 路由 | React Router | 登录、首页、工作台、分享页、后台模块页都走真实 URL |
| UI 组件 | Radix UI / shadcn 风格组件 + 业务组件 | 可参考 `ui/*/src/app/components/ui/`，但生产工程单独维护组件库 |
| 样式 | Tailwind CSS v4 + CSS Modules/全局主题变量 | 保持前台深色工作台、后台管理台布局 |
| 服务端状态 | TanStack Query | 管理项目、任务、素材、审核列表等 API 数据 |
| 客户端状态 | Zustand | 管理工作台当前步骤、局部草稿、UI 面板状态 |
| API 请求 | fetch/axios 封装 | 统一 token、租户上下文、错误处理、刷新登录 |
| 实时进度 | SSE 起步，后续 WebSocket | 用于 AI 任务、视频生成、导出任务进度 |

### 后端

| 层 | 技术 | 说明 |
| --- | --- | --- |
| 主后端 | Python 3.11+ + FastAPI | 模块化单体，适合快速实现 API、依赖注入、OpenAPI 和 AI 任务集成 |
| ORM | SQLAlchemy 2.0 / SQLModel | 管理模型、查询和类型约束；MVP 可优先 SQLModel 降低上手成本 |
| 数据迁移 | Alembic | 管理数据库 schema 版本和迁移脚本 |
| 数据库 | PostgreSQL | 存储用户、租户、项目、脚本、审核、素材元数据 |
| 队列 | Redis + RQ（MVP 起步）/ Celery（复杂任务编排） | 链接解析、AI 生成、视频生成、TTS、导出等耗时任务 |
| 缓存 | Redis | 登录态、任务进度、热点配置缓存 |
| 文件存储 | S3 兼容存储，如 MinIO、阿里云 OSS、腾讯云 COS | 存视频片段、配音、场景图、导出文件 |
| 向量检索 | PostgreSQL pgvector 起步，后续可换 Qdrant/Milvus | 结构公式、爆款特征、原创度相似度检索 |
| API 文档 | FastAPI 自动生成 OpenAPI / Swagger UI | 给两个前端对接 |
| 鉴权 | JWT + RBAC + 租户上下文 | 后端强制品牌隔离，不能只靠前端过滤 |

Python 版后端更适合当前项目的原因：AI Provider SDK、文本处理、相似度计算、文件处理、音视频任务和数据分析生态更成熟；FastAPI 自动生成 OpenAPI，便于前后台联调；RQ/Celery 可以把耗时任务从 API 请求中拆出去，保留模块化单体的简单部署方式。

MVP 阶段建议优先使用 `FastAPI + SQLModel + Alembic + PostgreSQL + Redis + RQ`，降低实现复杂度。任务依赖变复杂、需要定时任务或复杂重试策略后，再升级为 Celery。

## 前台页面架构

前台生产前端放在 `apps/front-web/`，负责品牌方运营和内容创作者的完整创作流程。`ui/ui-front-web/` 只作为设计参考，不能作为最终业务前端继续扩展。

前台生产工程需要从一开始支持真实路由、API 请求、登录态、项目状态恢复和任务进度展示，而不是继续依赖原型里的 `currentView` / `activeStep` 本地切换。

### 前台页面清单

| 页面 | 设计参考 | 生产页面建议 | 作用 | 路由 |
| --- | --- | --- | --- | --- |
| 登录页 | `ui/ui-front-web/src/app/components/Login.tsx` | `apps/front-web/src/app/pages/LoginPage.tsx` | 用户账号登录 | `/login` |
| 注册页 | `Register.tsx` | `RegisterPage.tsx` | 新用户注册 | `/register` |

| 步骤 1：全局设定 | `GlobalSettings.tsx` | `features/workflow/GlobalSettingsStep.tsx` | 视频比例、类型、平台 | `/projects/:id/workspace?step=global` |
| 步骤 2：产品卖点 | `SellingPoints.tsx` | `features/selling-point/SellingPointStep.tsx` | Brief、模板上传、卖点资产库 | `/projects/:id/workspace?step=selling-points` |

### 前台状态流

UI 原型中的状态：

```text
currentView: login | register | home | workspace
activeStep: global | selling-points | viral-analysis | storyboard | scene-role | video-gen | dubbing | preview | analytics
```

生产前端必须以后端项目状态为准：

```text
Project
  id
  tenantId
  ownerId
  status: draft | analyzing | scripting | auditing | generating | completed | archived
  currentStep
  stepStates[]
```

前端页面刷新时通过 `GET /api/projects/:id` 恢复项目状态，而不是依赖浏览器内存中的 `activeStep`。URL 上的 `step` 只表示当前想打开的步骤，是否允许进入由后端项目状态决定。

拆分原则：

| 原则 | 说明 |
| --- | --- |
| 页面组件只负责编排 | API 请求、状态转换和业务校验不要散落在 UI 子组件里 |

| 生成类按钮走任务接口 | 视频、配音、脚本生成都返回 `taskId`，前端轮询或订阅任务进度 |
| 分享页只读 | 分享链接必须由后端校验 token、版本和可见范围 |

## 后台前端页面架构

后台生产前端放在 `apps/admin-web/`，负责系统超级管理员、品牌管理员、审核员和技术运维人员的管理操作。`ui/ui-admin-web/` 只作为后台页面设计参考。

后台前端从一开始就要围绕权限和租户隔离实现，菜单是否可见、数据是否可操作都必须由后端权限返回结果决定，不能只在前端写死角色判断。

| 投放数据 | `analytics` | 播放、互动、转化、A/B 测试 |
| 系统权限 | `auth`、`tenant`、`system_log` | 租户、用户、角色、权限、操作日志 |

### 后台前端拆分原则

| 原则 | 说明 |
| --- | --- |
| 菜单由权限生成 | 后端返回当前用户可访问模块，前端按权限渲染菜单 |
| 管理列表标准化 | 表格、筛选、分页、批量操作抽成通用组件 |
| 审核操作必须二次确认 | 通过、驳回、删除、导出等操作需要确认和操作日志 |
| 租户上下文显式展示 | 品牌管理员只能看到本品牌；超级管理员切换品牌时页面要明确提示 |
| 后台不直接复用前台工作台状态 | 后台查看项目和脚本应走管理接口，避免绕过审核和权限边界 |

## UI 原型到生产前端的迁移方式

`ui/` 目录里的代码价值主要是页面视觉、布局、交互文案和业务流程参考。生产前端不应直接在 `ui/ui-front-web/`、`ui/ui-admin-web/` 上继续扩展，而应在 `apps/` 下重新建立可长期维护的前后端分离前端工程。

### 目录定位

| 目录 | 定位 | 是否继续写业务代码 |
| --- | --- | --- |
| `ui/ui-front-web/` | 前台 UI 原型参考 | 否 |
| `ui/ui-admin-web/` | 后台 UI 原型参考 | 否 |
| `apps/front-web/` | 前台生产前端 | 是 |
| `apps/admin-web/` | 后台生产前端 | 是 |
| `server/` | 后端 API 与 Worker | 是 |

### 新前端工程初始化建议

第一阶段建议直接新建两个 Vite React TypeScript 工程：

```text

apps/admin-web/
```

每个生产前端都应具备：

| 能力 | 说明 |
| --- | --- |

| API Client | 统一处理 token、错误、租户上下文 |

| 规则 | 说明 |
| --- | --- |

## 异步任务设计

耗时能力必须进入队列，避免 API 超时和重复提交。

| 队列 | 任务 | 触发来源 |
| --- | --- | --- |
| `parsing` | 抖音/小红书链接解析、数据清洗 | 前台步骤 3 |
| `script-generation` | Brief 优化、结构分析、分镜脚本生成 | 前台步骤 2/4 |
| `compliance` | 合规检查、原创度检测 | 前台步骤 4、后台审核 |
| `video-generation` | 按分镜生成视频片段 | 前台步骤 6 |
| `dubbing` | TTS、对口型处理 | 前台步骤 7 |
| `export` | 脚本下载、视频导出、报告导出 | 前台步骤 4/8、后台报表 |

任务状态建议统一：

```text
pending -> running -> succeeded
                 |-> failed
                 |-> cancelled
```

关键要求：

| 要求 | 原因 |
| --- | --- |
| 任务必须有 `tenantId`、`projectId`、`createdBy` | 保障租户隔离和审计 |
| 任务必须支持幂等 key | 防止用户重复点击导致重复生成和重复扣费 |
| 任务结果必须落库 | 前端刷新后能恢复进度 |
| 失败原因要结构化 | 便于后台解析日志和运维排查 |

## 多租户与权限策略

后端所有业务数据都必须带 `tenantId`，并通过服务端权限校验过滤。

| 角色 | 权限边界 |
| --- | --- |
| 普通前台用户 | 只能访问本租户内自己创建或被授权协作的项目 |
| 品牌管理员 | 只能管理本品牌项目、素材、知识库和审核任务 |
| 审核员 | 只能处理分配给自己的审核任务 |
| 系统超级管理员 | 可查看和配置全局数据，但关键操作必须写操作日志 |

不能依赖前端传入的 `tenantId` 作为最终可信来源。后端应从 JWT/session 中解析租户上下文，并在查询层强制拼接租户条件。

## 主要风险与处理方式

| 风险 | 处理方式 |
| --- | --- |
| 后端模块化单体变成大泥球 | 每个业务域独立 router、schema、service 和 repository，不跨模块直接写表 |
| 前台步骤状态和后端状态不一致 | 项目步骤状态以后端为准，前端只展示和提交动作 |
| 用户重复点击造成重复生成 | 所有生成类接口使用幂等 key 和任务状态锁 |
| AI 任务失败难排查 | 每个任务记录 provider、输入摘要、错误码、耗时和重试次数 |
| 租户数据泄露 | 服务端统一注入 tenant scope，禁止只靠前端筛选 |
| 审核记录被覆盖 | 审核记录和脚本版本使用追加式快照，不做物理覆盖 |
| 素材文件失控 | 文件元数据入库，删除走软删除和定期清理任务 |
